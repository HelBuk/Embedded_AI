\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
This project investigates practical Edge-AI deployment for the Real-Time fastener detection on
Raspberry Pi 4/5, with and without Hailo-8 AI accelerator. It targets a detection on a
conveyer belt with motion \( \approx 2 cm/s\), using an IDS uEye camera with maximum 21 FPS capability.
A lightweight YOLO variants (v8n/v8s/v10n/v10s/v11n/v11s) and a small RT-DETR-R18 transformer model
are trained via transfer learning on a domain-specific fastener dataset.
Four classes of objects are used during the training: machine screws, wood screws, nuts
and washers. An additional fifth class is used to identify incomplete parts of the object, when neither
a human, not a model can correctly classify an object. The dataset is prepared with the help of Roboflow framework, and it consists of 2131 augmented
960x960 grayscale images. Models are exported to ONNX format and compiled with the Hailo toolchain
(ONNX \(\to\) HAR \(\to\) HEF) using INT8 post-training quantization from a calibration set.  \\
A discussion of the annotation format choices, compilation workflow and on-device inference constraints is
provided in the literature overview section. \\
Evaluation performed based on standard detection metrics
(IoU, AP, mAP@0.50 and mAPP@[0.5:0.95]) and runtime
(latency/FPS). On GPU, all tested YOLO versions archived competitive accuracy on the gathered dataset.
While on Raspberry PI 4/5 CPU, real-time throughput is not met, Hailo accelerator shows significantly
higher raw inference capacity, having hardware benchmarks \( \approx 142 FPS\), while Pi 5 pipeline
delivers \( \approx 1 FPS\). However, the archieved inference accuracy after
the performed quantization is visibly lower than the pure YOLO PyTorch checkpoint inference.
The studies on image size and NMS settings, and briefly analyzed quantization effects on small,
fine-grained targets are reported.

\chapter{Introduction}

\section{Motivation}

With the increase of interest in AI usage on small devices a problem of the on-deploy arises.
In the past decade Artificial Intelligence field made a big progress in solving complex problems
of Natural Language processing, Computer Vision and Robotics. However, most of the time
such models require a lot of both, data and computing resources. For instance, the full training
of state-of-the-art open source Large Language Model (LLM) - LLaMA (3 400 B)
\cite{meta_llama3_github} would take approximately 125 million years on
a Raspberry Pi (ARM Cortex A53) and a thousand GPU datasenter is required to train the model
in a proper amount of working days. In many real production settings, such highly complex
models are unnecessary; instead, there is a stronger demand for fast processing on small,
resource-constrained devices. The trade-off between accuracy and speed becomes a central
point of interest. This work aims to research a prossibily to perform a Real-Time inference
on a constraned platform such as a Raspberry Pi 5 and cover a full chain from data collection
on a real camera, through training and quantization, to deployment with the use of Hailo-8
accelerator. We provide empirical data on the trade-off between different detector architectures
(Yolo models family and RT-DERT), input resolutions, and quantization strategies. This project
evaluates these small detection models on a fastener dataset and measures their behaviour under
time and memory constraints.

\section{Limitations}
The project is subject to several practical and methodological limitations:

    \begin{itemize}
        \item \textbf{Narrow application domain:} The detector is trained and evaluated
        only on four fastener classes: machine and wood screws, nuts and washers) in a single
        conveyer-belt setup. The results do not directly generalize to arbitrary industrial scenes.
        \item \textbf{Restricted hardware platform:} All on-device experiments are performed on a
        Raspberry Pi 4 \& 5 with 4 and8 GB RAM, respectively, and a single Hailo-8 accelerator.
        No comparison is made to other edge accelerators or microcontrollers.
        The conclusions are specific to this hardware combinations.
        \item \textbf{Model Choice} The experiment comparison is restricted to YOLOv8, YOLOv10, YOLOv11
        nano and small variants as well as RT-DETR-R18. Moreover, only classic optmization strategies
        provided by Hailo compiler are explored.
        \item \textbf{Dataset constraints} The Transfer Learning is performed only on a
        limited to 2131 grayscale images 960$\times$960 resolution. Although data augmentation
        is applied, the number of unique physical parts, lighting conditions remains limited
        compared to large public datasets.
    \end{itemize}

\section{Contributions}

    Within these limitations, the main contributions of this specialization project are:

    \begin{itemize}
        \item \textbf{Domain-specific dataset:} Collection and annotation of a grayscale fastener dataset captured
              with an IDS uEye industrial camera, including four main fastener classes and a fifth miscellaneous
              class for incomplete or ambiguous parts.

        \item \textbf{Model training and comparison:} Training and evaluation of seven detectors
              (YOLOv8n/s, YOLOv10n/s, YOLOv11n/s, and RT-DETR-R18) on the fastener dataset, including experiments
              with two input resolutions (640$\times$640 and 960$\times$960) and analysis of their precision, recall,
              and mAP scores.

        \item \textbf{Edge deployment pipeline:} Implementation of a deployment workflow from PyTorch
              checkpoints to ONNX, HAR, and HEF, followed by on-device inference on Raspberry Pi 5 and the Hailo-8
              accelerator. This includes configuring post-training INT8 quantization and integrating Hailo’s NMS
              post-processing.

        \item \textbf{Runtime benchmarking:} Systematic measurement of latency and throughput on the target hardware,
              comparing CPU-only inference on Raspberry Pi 5 with accelerated inference on Hailo-8, and relating these
              results to the throughput requirements of the conveyor-belt setup.

        \item \textbf{Practical guidelines:} A set of concrete recommendations and configuration examples for future
              Edge-AI projects at NTNU, covering camera setup, dataset preparation, model selection, and Hailo/ONNX
              toolchain usage.
    \end{itemize}

\section{Introduction to Object Detection with Deep Learning Models}

Artificial Intelligence (AI) is a broad term covering a set of algorithms and operations on
matrices and vectors that enable computers to perform a big variety of tasks in language
understanding and translation, object recognitions, robotic performance etc.
We will consider only models performing object detection tasks, mostly having CNN \cite{krizhevsky2012imagenet}
and Transformer \cite{vaswani2017attention} architectures.

At a high level, a neural network model can be seen as a parameterized function
\[
    f_\theta : \mathbb{R}^{H \times W \times C} \rightarrow \mathcal{Y},
\]

where the input is an image with height \(H\), width \(W\), and \(C\) channels, and the output space
\(\mathcal{Y}\) depends on the task. For object detection,
\(\mathcal{Y}\) consists of a set of bounding boxes (see section 2.2) and class probabilities
for each detected object.

The vector \(\theta\) contains all trainable (optimized) parameters (weights and biases)
of the network. \\

It is common to use terms \enquote{training} and \enquote{inference} \cite{Goodfellow2016}.
By training we understand some sort
of iteration through a set of examples, so the model \enquote{learns} coefficients, approximating
the distribution of the dataset. The more examples we have, the bigger share of general
distribution we cover. We start training with some state of parameters (weights) \(\theta\).
During training, parameters are iteratively updated so model’s outputs
match the desired targets on a labeled dataset. This can be described as an optimization task,
we iteratively search for coefficients, which minimise the difference of the chosen metric,
computed on a model-labeled and human-labeled pictures. For example, for object detection we
want to decrease a localization loss (how well the predicted boxes align with the true boxes)
and a classification loss (how well the predicted classes match the true classes).
Metrics used to evaluate the quality of the training are described in detail in
the Chapter \ref{chap:literature}.
During inference (forward pass), parameters are fixed, and model simply computes
\(f_\theta(x)\) for an input image \(x\). \\


The size of a neural network can be characterized by the number of parameters
and the amount of computation (e.g.\ FLOPs) required per forward pass.
Larger models typically have higher capacity and can represent more complex functions,
which often leads to better accuracy when sufficient training data is available. \\

However, on embedded devices such as Raspberry Pi 4/5, model size has
several practical consequences:

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Memory usage:} Large models may not fit into the limited RAM available on edge devices.
    \item \textbf{Latency:} More parameters and layers lead to higher inference time, reducing FPS and making
          real-time processing harder to achieve.
    \item \textbf{Energy consumption:} Heavier models require more operations and therefore more power,
          which is critical for battery-powered systems.
\end{itemize}

For Edge-AI applications, it is necessary to balance accuracy and model size/computational
cost. This trade-off leads to the use of lightweight architectures
(e.g. nano/small variants) and
techniques such as quantization and hardware acceleration. \\

Training a complex detector requires large, diverse datasets and big compute
resources. So, it is common to rely on transfer learning. In transfer learning, a model
is first trained on a large dataset (such as COCO \cite{Lin2014COCO}) and then adapted to a specific task
or domain  by fine-tuning on a smaller, domain-specific dataset. \\

In the context of this project, transfer learning enables the use of YOLO and RT-DETR models
pretrained on large datasets, which are then fine-tuned on the fastener dataset.
This approach reduces training time and improves accuracy compared to training
an equivalent detector from random weights initialization, while still allowing the model to adapt
to the specific visual properties of screws, nuts, washers, and miscellaneous parts.

\section{Datasets and Annonation strategies for Detection Tasks}
    Object detection models localize objects on an input picture or on a set of video frames.
    Localization can be performed by different approaches, the most relative to this work are:
    \begin{itemize}
        \item Axis-aligned bounding  box (AABB): (x, y, w, h), which is cheap to annotate
            and fast to predict.
        \item Oriented/rotated bounding box (OBB): apart from AABB an angle $\theta$ of
            the box is introduced,  which is a bit costlier to label.
        \item Polygon: a list of vertices tracing the object boundary. Provides precise
            geometry, however is time-consuming to label.
        \item Pixel mask (\enquote{painted area}) - most precise 2D shape, ideal for measurement
            and robotics, heaviest to annotate and train on.
    \end{itemize}

    Choosing the right localization strategy should be guided by the structure of
    the available pretrained weights. Training large detectors from scratch is
    both resource- and time-intensive. For example, Ultralytics estimates that
    training YOLOv5 on COCO (118k images, 300 epochs) on a single
    NVIDIA V100-16GB takes approximately $n/s/m/l/x \approx 1/2/4/6/8$ days,
    respectively \cite{UltralyticsYOLOv5Quickstart}. Collecting and annotating
    a dataset of that scale is even more time-consuming. Consequently,
    it is preferable to start from weights pretrained on a dataset whose
    \emph{labeling granularity} matches the task (e.g., axis-aligned boxes
    vs.\ oriented boxes vs.\ masks). If the required annotation is more
    detailed than the pretraining labels, an additional annotation
    effort is needed for transfer learning. Then, if axis-aligned bounding
    boxes (AABB) are too coarse for small or complex objects, a
    richer localization (e.g., oriented boxes or instance masks) to meet
    accuracy requirements would be a better choice.

    Mentioned earlier COCO dataset \cite{Lin2014COCO} is the common
    detection benchmark. It is big enough, varied, well-annotated and
    permissively licensed. The dataset contains photos of 91 objects
    types with a total of 2.5 million labeled instances in 328k
    images.

    COCO’s \cite{Lin2014COCO} official detection annotations are
    axis-aligned boxes only (bbox: [x, y, width, height]). There
    are no oriented boxes in COCO, so the standard YOLOv8/YOLO11
    \cite{Redmon2016YOLO} \textit{detect} checkpoints (trained
    on COCO 2017) learn AABB by default:

    It is also possible to convert OBB annotation to AABB annotation with some
    loss of information. In order to do so these steps can be followed.

    Let $w,h$ be side lengths and $\theta$ the rotation (radians, CCW). The tight
    axis-aligned box around the rotated rectangle has
    \begin{align}
    W_{\text{AABB}} &= \lvert\cos\theta\rvert\, w + \lvert\sin\theta\rvert\, h, \\
    H_{\text{AABB}} &= \lvert\sin\theta\rvert\, w + \lvert\cos\theta\rvert\, h .
    \end{align}
    With the same center $(c_x,c_y)$,
    \begin{align}
    x_{\min} &= c_x - \frac{W_{\text{AABB}}}{2}, &
    x_{\max} &= c_x + \frac{W_{\text{AABB}}}{2}, \\
    y_{\min} &= c_y - \frac{H_{\text{AABB}}}{2}, &
    y_{\max} &= c_y + \frac{H_{\text{AABB}}}{2}.
    \end{align}

    If the oriented box is given by four corners $(x_i,y_i)$, the enclosing AABB is
    \begin{align}
    x_{\min}=\min_i x_i,\quad x_{\max}=\max_i x_i,\qquad
    y_{\min}=\min_i y_i,\quad y_{\max}=\max_i y_i .
    \end{align}

    \textbf{COCO bbox} uses $[x_{\min},\,y_{\min},\,\text{width},\,\text{height}]$, then: \\
    \begin{align}
    \text{bbox}_{\text{COCO}}
    = \bigl[\, x_{\min},\; y_{\min},\; x_{\max}-x_{\min},\; y_{\max}-y_{\min} \,\bigr].
    \end{align}

    \textbf{YOLO txt} uses normalized $(x_\text{center},y_\text{center},w,h)$, then: \\
    Given image size $(W_{\text{img}},H_{\text{img}})$,
    \begin{align}
    x_\text{center} &= \frac{x_{\min}+x_{\max}}{2\,W_{\text{img}}}, &
    y_\text{center} &= \frac{y_{\min}+y_{\max}}{2\,H_{\text{img}}}, \\
    w               &= \frac{x_{\max}-x_{\min}}{W_{\text{img}}}, &
    h               &= \frac{y_{\max}-y_{\min}}{H_{\text{img}}}.
    \end{align}


\section{The model choice}

    For Edge AI, the trade-off between computation speed and
    memory availability is critical. A model must not only deliver
    sufficiently high accuracy, but also remain compact to fit
    onto resource-constrained devices such as microcontrollers.

    YOLO models family (see Table \ref{tab:yolo-timeline}) presents state-of-the-art
    lightweight versions of model small and efficient enough to be used
    on Edge-devices. The family shows good results for both - the prediction
    accuracy and inference speed.

    Before YOLO \cite{Redmon2016YOLO} the most common detection approaches used
    two-stage pipelines. The first stage was responsible for generation of
    the box, the other one for classification. It allowed to archive high
    accuracy, but kept these models slow. The YOLO series introduced a single-one
    stage detector - a single convolutional model predicts bounding boxes and
    class probabilities in one pass over the image. It speed up the inference and
    allowed YOLO to compete among Real-Time Inference models.

    There also exist some other successful approaches in real-time detection. One
    of the earlier mentioned models - RT-DETR \cite{lv2023rtdetr} - uses a Transformer-based
    architecture. By using transformer decoder, it removes NMS entirely,
    as was done in YOLOv10 too. It allows RT-DETR model to perform excellent on GPU

    still remain more parameter-efficient and faster on low-power device or CPUs. \\

    The other well suitable for the Edge detection model is NanoDet \cite{nanodet}. It targets
    fast CPU inference and deployment on edge devices. It can be as small as 0.95
    million parameters, which is smaller than YOLOv8n and Yolov11n models.
    Authours report a quantized INT8 NanoDet model having approximately 97 FPS on

    \textbf{Summary of model comparison:} For edge hardware with limited or no GPU,
    YOLOv11-n or NanoDet would be preferred
    due to their small size (with YOLO offering higher accuracy at a bit
    larger size). With a GPU or NPU, YOLOv11-s or even RT-DETR can be considered.

\section{Hailo Compiler}

    Hailo compiler \cite{hailo_manual} is needed to load user's models to the Hailo devices.
    The final result of the compiler is a binary file \texttt{.hef}.
    The standard DataFlow for this conversion consists of the three main steps:

    \begin{itemize}
        \item Translation of the source model to Hailo model;
        \item Optimization of model parameters;
        \item Compilation process itself;
    \end{itemize}


    \begin{figure}[H]
      \centering
      \includegraphics[width=0.8\linewidth]{pics/out_graph/hailo_flow.pdf}
      \caption{Build Process \cite{hailo_manual}}
      \label{fig:hailo_flow}
    \end{figure}

    The first step in the Figure \ref{fig:hailo_flow} is a translation from the user's
    model to the \texttt{.har} representation. The Hailo Translation API parses user's model
    and produces a \texttt{.har} (Hailo ARchive).

    \begin{itemize}
        \item HAR is a zip package that contains:
        \begin{itemize}
            \item HN— \enquote{Hailo Network}: a JSON graph of the network (layers,
                tensor shapes/dtypes, connections, metadata).
            \item NPZ—NumPy arrays with the floating-point weights(and sometimes
                other tensors like batch normalization params).
        \end{itemize}
    \end{itemize}

    This step is needed, so the parameters of the model are normalized from the other
    possible checkpoint configurations (used operation and attributes names, FP32 weights),
    and the optimizer has a clean input.

    The second step is model optimization. The key part of the optmization is the conversion
    of the model from FP32 to INT8. It is done with an additional run of calibrarion module.

    There exist different ways to quantize a model. To my knowledge, Hailo Compiler is using
    the Linear Quantization:

    Key benefits from this approach is its efficiency, support by major DL frameworks and easy
    implementation \cite{Han_6.5940_2024}. However, the drawback is a visible precision loss as many nearby
    floating-point values collapse to the same quantized level. Layers with large
    dynamic range (e.g., softmax) are more sensitive to this method.

    Assume an input floating-point value, the linear quantization is
    \[
      q = \operatorname{round}\!\left( Z + \frac{r}{S} \right).
    \]
    \paragraph{Where}
    \begin{itemize}
      \item $r$: original 32-bit floating-point number
      \item $q$: quantized representation (integer)
      \item $S$: scale factor (step size)
      \item $Z$: zero point (integer), which allows $r=0$ to be represented exactly by the integer $Z$
    \end{itemize}

    Dequantization is defined by the formula:
    \[
      r \approx (q - Z)\,S.
    \]

    It is also illustrated at the Figure \ref{fig:quantization}
    \begin{figure}[H]
      \centering
      \includegraphics[width=0.7\linewidth]{pics/out_quant/quantization.pdf}
      \caption{Build Process \cite{Han_6.5940_2024}}
      \label{fig:quantization}
    \end{figure}

    In order to perform this optimization, the calibration set of raw, unlabeled samples is gathered.
    It should match a real input distribution (color space, normalization). The compiler uses this
    set to run a neural network on it and logs per-tensor activation distributions. So, it records
    min/max values and percentiles. By doing so, an optimizer gets $r_{min}$ and $r_{max}$ values.
    Which are used to compute $q_{min}$, $q_{max}$ and $Z$ - point (see Figure \ref{fig:quantization}).
    It is important to do it per tensor as different layers produce values with very different
    ranges/outliers. Choosing ranges from their actual distributions minimizes quantization error.


    The last step is a compilation itself, which the model is compiled to a binary file \texttt{.hef}.
    The compiler is responsible for allocation hardware resources, so the highest possible FPS can be
    archived. It performs it by mapping neural network layers onto the hardware \cite{rptu_eml_ch12_2025} (compute elements,
    memory elements, and control elements) and schedule their execution under the chip's resource
    constraints. If the network is too large, the compiler will partition the network into several
    contexts, allowing bigger models still run with some performance overhead.
    The compiler might tile large tensors, split layers into smaller pieces
    to fit into memory and to utilize parallelizm. Key strategy of this hardware mapping is to perform
    as many computation as possible (possibly for difference layers) on the kept on the chip memory
    tensors. As part of scheduling, compiler also defines the data flow from layer to layer, chaining
    producers and consumers layer clusters. For example, while the layer i is computed on one side of the
    chip, another part of the chip might start executing layer i+1 (Illusration: \ref{fig:conv_reuse}).
    This schedule is constructed during the
    compilation step. Apart from the execution plan, compiler also performs on-chip Non-Maximum
    Suppression (NMS) fusion for models like YOLO. NMS algorithm performs deduplication of several
    predicted for the same object boxes. For instance, the screw could be with different probabilities be
    predicted both as machine and wood screw. So, the post-processing NMS is performed to keep only the most
    suitable box. Hailo's compiler can inregrate NMS as the final layer of the network, so it runs on the
    hailo itself and not on the CPU after the inference. It improves the performance not only due to localization
    of computation, but also due to reduced data transfer - only filtered detections are sent to the
    Raspberry Pi.

    \begin{figure}[H]
      \centering
      \includegraphics[width=0.7\linewidth]{pics/conv_reuse.pdf}
      \caption{Example of the layers reuse: convolutional reuse (Inspired by \cite{emer_sze_chen_2019_dnn_accel_tutorial})}
      \label{fig:conv_reuse}
    \end{figure}

    The final Hailo Executable File contains:
    \begin{itemize}
        \item Low-level program for the target device (layer schedule, the memory buffer addresses/sizes,
            instruction sequences etc.)
        \item Weights and biases
        \item Metadata and calibration information
    \end{itemize}

\section{Summary of the Literature Study}
\label{sec:lit-summary}

The literature review establishes the technical context and design space for real-time object detection
on constrained edge hardware (Raspberry Pi 4/5) with optional NPU acceleration (Hailo-8).
We surveyed (i) detection formulations and annotation strategies, (ii) dataset options and label formats,
(iii) lightweight detector families suitable for edge deployment,
and (iv) compilation/quantization toolchains required to execute modern models on dedicated accelerators.

\textbf{Detection task \& annotations.}
Object detection can be localized with axis-aligned boxes (AABB), oriented boxes (OBB),
polygons, or pixel masks. While OBB/polygons align better with prolongated parts (e.g., screws),
AABB remains the best choice for transfer learning with common pretrained weights (e.g., COCO)
and for real-time deployment. The review also summarizes conversions from corner points
and the practical AABB enclosure of OBBs, together with format mappings to COCO JSON and YOLO TXT.
This motivates our use of AABB for the fastener domain to minimize engineering.

\textbf{Datasets.}
COCO is the dominant pretraining source for AABB detectors and ensures strong generalization,
whereas DOTA provides OBB \texttt{*-obb} variants.
A domain-specific fastener set (MVTec Screws) offers OBB labels but is limited in scale.
Due to the fact that public datasets rarely contain fasteners, the study supports
a compact, grayscale, task-specific dataset and to perform transfer learning from pretrained on COCO weights.

\textbf{Model families for edge.}
Single-stage YOLO variants remain the most practical for low-power deployments
due to accuracy–latency trade-offs. In the past years YOLO evolved toward anchor-free heads,
improved backbones, and—in v10—NMS-free training;
YOLOv11 focuses on higher accuracy per parameter and streamlined exports.
Transformer-based RT-DETR remover NMS and scales well on GPUs,
but it is typically more compute-expensive on CPUs/edge. Ultra-samll models like NanoDet can reach
very high CPU FPS with INT8 quantization, at the expense of accuracy. Overall, the review motivates
evaluating YOLO -nano/-small variants first for Raspberry Pi CPUs, with RT-DETR as
a comparative reference when acceleration or higher latency budgets exist.

\textbf{Compilation and quantization.}
Executing modern detectors on an NPU requires a specific toolchain. The Hailo flow
(ONNX $\rightarrow$ HAR $\rightarrow$ HEF) translates graphs, calibrates activations,
and performs graph/resource scheduling. The study explains linear INT8 PTQ
(scale/zero-point, per-tensor ranges from calibration statistics), YOLO post-process/NMS,
and context partitioning when models exceed on-chip resources.
These mechanisms are important for moving the entire detection path
(tensor in $\rightarrow$ filtered detections
out) onto the accelerator, minimizing CPU load and PCIe/host transfers.

\textbf{ONNX as an interchange.}
ONNX is identified as the stable intermediate for exporting PyTorch checkpoints and enabling downstream
compilation. Its operator coverage and ecosystem support reduce model operations variability across
training and deployment.

\paragraph{Implications for this project.}
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Labeling choice:} We will use AABB to align with pretrained YOLO checkpoints and simplify
  the Hailo export pipeline. However, the use of OBB is still posible and might improve the quality of the detection.
  \item \textbf{Model shortlist:} We prioritize YOLOv8/10/11 -nano/-small
  for Raspberry Pi-only baselines. We also include RT-DETR-R18 - YOLO competitor, for transformer reference
  and for the speed/quality tradeoff experiments.
  \item \textbf{Tooling:} Standardize on PyTorch $\rightarrow$ ONNX and the Hailo compiler with INT8 PTQ
  using a calibration set that matches deployment preprocessing.
  \item \textbf{Performance strategy:} For strict real-time throughput,we run experiments on Hailo-8 with
  post-processing
\end{itemize}

\paragraph{Gaps and risks.}
OBB supervision could further improve fine orientation for screws but would require new pretraining
or costly relabeling. Quantization sensitivity on small, fine-grained targets remains a risk. Careful
calibration selection and post-training checks are necessary.
Finally, runtime on Raspberry Pi pipelines is latency-limited, so the use of accelerator is crucial for
real-time performance.

\section*{Metrics description}
\textbf{Metrics description}:

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Intersection over Union (IoU)}: \\
            For a predicted box \(p\) and ground-truth box \(g\), the IoU formula is: \\
            \[
                \IoU(p,g) = \frac{|p\cap g|}{|p\cup g|}
            \]
            IoU plays role of evaluating an object localization. \\
            It quantifies the overlap between a prediction and ground truth bounding boxes by calculating
            the ratio of the intersection (overlapping area) to the union (total area covered by both boxes).
            IoU is a building block for calculating mAP. \\
            The resulting score is a value between 0 and 1, which quantifies how accurately a model has located an
            object in an image. A score of 1 represents a perfect match, while a score of 0 indicates no
            overlap at all. \\
            The key part of using IoU is to define \textit{\enquote{IoU threshold}}. This threshold is a predefined value
            (e.g., 0.5) that determines whether a prediction is correct. If the IoU score for a predicted box is
            above this threshold, it is classified as a \enquote{true positive} (TP).
            If the score is below, it's a \enquote{false positive} (FP). \\
            This threshold directly influences other performance metrics like Precision and Recall. \\

    \item \textbf{Precision and Recall}: \\
            Precision defines the proportion of true positives among all positive predictions,
            measuring the ability to avoid misclassification. \\
            \[
                Precision (P) = \frac{\TP}{\TP+\FP},
            \]

            On the other hand, Recall calculates the proportion of true positives among all actual
            positives, measuring the model's ability to detect all instances of a class. \\
            \[
                Recall (R) = \frac{\TP}{\TP+\FN},
            \]
    where \\
    TP - True Positive, FP - False Positive, TN - True Negative and FN - False Negative
    predictions. \\

    \item \textbf{Average Precision (AP)}: \\
        AP computes the area under the precision-recall curve \cite{Goodfellow2016}, providing a single value that encapsulates
        the model's precision and recall performance. \\
        \[
            \AP_{\tau} = \int_{0}^{1} p(r;\tau)\,dr,
        \]
        In order to build the precision-recall curve, the score (confidence) threshold (t) is used:
        \begin{itemize}[leftmargin=1.5em]
            \item Every detection has a score $s \in [0,1]$.
            \item We sweep t from high $\to$ low (equivalently sort detections by score desc and add them one-by-one).
            \item At each t we keep detections with $s \ge t $ and recompute P/R.
            \item This sweep produces the P–R curve.
            \item AP is the area under this P–R curve;
        \end{itemize}
        \begin{figure}[H]
          \centering
          \includegraphics[width=0.8\linewidth]{pics/pr_concept.pdf}
          \caption{Precision–Recall curve.}
        \end{figure}



    \item \textbf{Mean Average Precision (mAP)}: \\
        Another metric - mAP,  extends the concept of AP by calculating the average AP values
        across multiple object classes. \\
        This is useful in multi-class object detection scenarios to provide
        a comprehensive evaluation of the model's performance.
        \[
            \mAP_{0.50} = \frac{1}{C}\sum_{c=1}^{C}\AP_{c,\,0.50},
        \]
        \[
            \mAP_{[0.50:0.95]} = \frac{1}{C}\sum_{c=1}^{C}\frac{1}{10}
                                 \sum_{k=0}^{9}\AP_{c,\,(0.50+0.05k)}.
        \]
        The parameter \(C\) is the number of classes for which detection and classification
        are performed. \\
        The subscript \(0.5\), as well as the set [0.50:0.95], denotes the IoU threshold: predictions
        with \(\mathrm{IoU}\ge 0.5\) are counted as true positives (TP). \\

\end{itemize}

\section{Experimental Setup}

We trained seven models (Yolo v8, v10, v11 -n/-s and RT-DETR-R18) to provide
an overview of their performance in terms of accuracy and speed. For the training
NVIDIA GeForce RTX 3070 was used, which provides up to 20 TFLOPs of FP32 (single-precision)
and has 8GB of RAM.
After the training and evaluation on the GPU, models were deployed on Raspberry Pi 5
for the on-device speed benchmarking and demo detection streaming.

Then, models were optimized and compiled to the \texttt{.hef} format, so they could be run on a
Hailo-8 AI accelerator with 26 TOPS.

\section{Results}

\subsection{Runtime analysis}

Figure~\ref{fig:detectors_640_combined} summarises the runtime characteristics of all evaluated detectors
on the screw test video at $640\times640$ input resolution on host CPU. For all models, the preprocessing
and postprocessing stages are relatively cheap, staying around 2\,ms and below 0.5\,ms per frame
respectively, The total latency is dominated by the inference time.

Among the YOLO variants, the nano models (YOLOv8n, YOLOv10n, YOLOv11n) achieve total runtimes between
31.4\,ms and 34.3\,ms per frame, which is equal to 30\,FPS. Despite small differences
in parameter count and GFLOPs, their inference times are very similar, with YOLOv8n being slightly
faster than YOLOv10n/YOLOv11n. The small models (YOLOv8s, YOLOv10s, YOLOv11s) double the parameter
count and GFLOPs compared to their nano version, which leads to a near-doubling of the inference
time (about 62–64\,ms) and a reduction to approximately 15\,FPS.

RT-DETR-R18 shows a significantly different runtime profile. With 21.9\,M parameters and an estimated
60\,GFLOPs, its inference time of 148.3\,ms leads to a total latency of 150.4\,ms per frame,
i.e.\ about 6–7\,FPS on the same CPU. While preprocessing and postprocessing remain comparable
to the YOLO models, the transformer-based backbone and head are substantially more expensive
than the convolutional YOLO architectures. \\

Figure \ref{fig:detectors_640_combined} highlights a clear trade-off between model complexity and real-time performance,
with the nano YOLO variants best suited for latency-constrained deployments on host CPU. Taking into an account
the hardware configuration of the host CPU (Table \ref{tab:cpu_specs}) and Raspberry Pi 5 CPU (Table \ref{tab:pi_specs}),
the scaling factor is $\approxeq 0.71 TF / 0.0768 TF \approxeq x9.25$ slower on Pi if compute-bound and
approximately x3 on practice.
Then an estimation of the model performance on Raspberry Pi 5: lands at 1.1 FPS (nano), 0.6 FPS (small)
and 0.24 FPS (RT-DETR).

\subsection{Performance overview}

As shown in the runtime overview subsection, the YOLO models demonstrated the best inference performance,
particularly the -nano variants. In this subsection, only the -nano versions of YOLO are compared against
each other, focusing on their runtimes when executed on the Raspberry Pi 5 CPU and their mAP performance. \\

Table~\ref{tab:val_summaries} compares the validation performance of the three nano
models on the screw validation set v8n, v10n and v11n. Overall, all architectures achieve strong detection
quality, with class mAP$_{50\mbox{--}95}$ values between 0.728 and 0.742.
YOLO8n attains the highest mAP$_{50}$ (0.964) and competitive mAP$_{50\mbox{--}95}$
(0.733), while YOLO11n slightly improves the overall mAP$_{50\mbox{--}95}$ to 0.742
at the cost of a marginal drop in precision (0.920 vs.\ 0.927). YOLO10n sits in between,
with the best mAP$_{50}$ (0.969) but a slightly lower mAP$_{50\mbox{--}95}$ (0.728). \\

Across classes, all three models perform best on nut, washer
and wood\_screw, where precision and recall are above 0.95
and mAP$_{50\mbox{--}95}$ reaches 0.76–0.91. In terms of runtime, all nano models
show very similar behaviour on the Raspberry Pi 5, with preprocessing around 8-9\,ms
and inference between approximately 1.0 and 1.1\,s per image. The differences in
latency (YOLO8n being slightly faster than YOLO10n and YOLO11n) are small compared
to the overall inference time, so model choice is primarily driven by the modest
accuracy differences rather than runtime on this platform. \\

From the comparison of these three models it seems that v8n is slightly better than
v10 and v11, as it shows both the highest mAP$_{50}$ and the lowest inference time,
however, models v10 and v11 have better trade-off between size and accuracy. \\

\subsection{Image size influence on model performance}

Table~\ref{tab:yolo11n_resolution} compares YOLO11n evaluated on the screw test set
at two input resolutions, $640\times640$ and $960\times960$. Overall, the model achieves
very similar performance at both scales: the mAP$_{50\text{--}95}$
stays mostly unchanged (0.737 vs.\ 0.740), while precision and recall slightly
improve at $960\times960$ (from 0.930/0.922 to 0.938/0.963). For most classes,
mAP$_{50}$ and mAP$_{50\text{--}95}$ either increase
(e.g.\ nut and wood\_screw) or stay almost identical (washer). The miscellaneous class
remains the most challenging: recall benefits from the higher resolution
(0.687 to 0.846), but its mAP$_{50\text{--}95}$ slightly decreases (0.522 to 0.516),
indicating that additional detections are partly offset by noisier localization or extra false positives.

The normalized confusion matrices in Fig.\ref{fig:yolov11n_cm_640} and Fig.\ref{fig:yolov11n_cm_960} provide
a qualitative view of these effects. At $640\times640$
(Fig. \ref{fig:yolov11n_cm_640}), most probability mass already lies on the diagonal,
with confusion between machine\_screw and miscellaneous,
and between wood\_screw and the background. At $960\times960$
(Fig.\ref{fig:yolov11n_cm_960}), the diagonal entries for machine\_screw,
nut, washer, and wood\_screw become slightly stronger,
reflecting the small gains reported in Table \ref{tab:yolo11n_resolution}. However, the
miscellaneous class continues to show the largest off-diagonal mass,
confirming that it is the main source of residual confusion.

Finally, the validation log at $960\times960$ reports an average CPU inference
time of 124.8\,ms per image (with 4.2\,ms for preprocessing and 0.5\,ms
for postprocessing), i.e.\ roughly 8\,FPS. Given the marginal accuracy gains
compared to $640\times640$, this highlights a clear resolution - speed trade-off:
higher input resolution yields slightly more stable detections on most classes,
but at a significant computational cost on the target hardware.

\subsection{Hailo impact}

The impact of offloading inference to the Hailo-8 accelerator is significant.
While the Raspberry Pi 5 CPU executes the nano models at around 1s per image
(see.\ Table \ref{tab:val_summaries}), the Hailo benchmark for the
compiled \texttt{yolov8n.hef} reports over 140 FPS in both HW-only and
streaming modes, with a hardware latency of only 10.8 ms per frame
(Table~\ref{tab:hailo-bench}). This corresponds to more than two orders
of magnitude improvement in throughput compared to pure CPU execution.
The HEF metadata in Table~\ref{tab:hef-meta} confirms
that the network is mapped to a single \texttt{yolov8n} context on the HAILO8
architecture, while Tables~\ref{tab:vstream} and~\ref{tab:nms-params} show
that both the input tensor and the YOLOv8-specific NMS post-processing
(including class-aware suppression and bounding-box limits) are integrated into
the accelerator pipeline. This means that the entire detection
stage from raw image tensor to filtered detections can be executed
on the Hailo device with minimal CPU involvement, enabling real-time operation
on the conveyor setup where the Raspberry Pi 5 alone is clearly insufficient.

\chapter{Hailo Compilation SetUp}

\begin{lstlisting}[caption={Export YOLO to ONNX for Hailo toolchain},label={lst:yolo-export-onnx}]
# ONNX export settings, friendly for accelerator toolchains
yolo export \
  model=.../best.pt \
  format=onnx \
  imgsz=960,960 \
  opset=12 \
  dynamic=False \
  simplify=True \
  nms=False
\end{lstlisting}

 \begin{lstlisting}[language=bash,caption={Parse ONNX to HAR with Hailo Translation API},label={lst:hailo-parser-onnx}]
hailo parser onnx \
  --hw-arch hailo8 \
  --net-name yolov11n_custom \
  --har-path .../yolov11n_parsed.har \
  --input-format NCHW \
  --tensor-shapes '[1,3,960,960]' \
  -y \
  .../best.onnx
\end{lstlisting}

    Hailo compiler parsed ONNX file with configuration:
    \begin{itemize}
        \item NMS added on the Hailo side
        \item YOLO models output three or six detection heads (depending on stride levels). But many exported
    ONNX graphs also include a concatenation node that merges these heads into one big tensor.
    Hailo wants the raw outputs before that concat, because this allows:

            \begin{itemize}
                \item better scheduling on hardware
                \item Hailo’s own optimized NMS
                \item less memory overhead
                \item cleaner graph structure
            \end{itemize}

        \item Hailo recommends using Conv head outputs as end nodes:

            \begin{itemize}
                \item /model.23/cv2.0/cv2.0.2/Conv
                \item /model.23/cv3.0/cv3.0.2/Conv
                \item /model.23/cv2.1/cv2.1.2/Conv
                \item /model.23/cv3.1/cv3.1.2/Conv
                \item /model.23/cv2.2/cv2.2.2/Conv
                \item /model.23/cv3.2/cv3.2.2/Conv
            \end{itemize}

    \end{itemize}

    \begin{lstlisting}[language=bash,caption={Hailo optimization with calibration set},label={lst:hailo-optimize}]
    hailo optimize --hw-arch hailo8 \
      --calib-set-path .../calib_nhwc_960.npy \
      --output-har-path .../yolo11n_quant.har \
      .../yolov11n_parsed.har
    \end{lstlisting}

    For YOLO11-n, the Hailo compiler (DFC 3.33.0) recognized a YOLOv8-like NMS structure but did not allow
    running the post-processing on the NN-core for this meta-architecture.
    Therefore, we offload NMS to the Raspberry Pi CPU, while the backbone and detection heads run on Hailo-8.

    \begin{lstlisting}[language=bash,caption={Compile quantized YOLO11n HAR to HEF on Hailo-8}]
    hailo compiler \
      --hw-arch hailo8 \
      --output-dir ... \
      .../yolo11n_quant.har
    \end{lstlisting}

    The yolo11n model required a 3-context mapping on Hailo-8 to satisfy resource
    constraints while preserving performance.
